## Overview

The first line `turso dev` printed was `sqld listening on port 8080.` I was looking into Turso's Rust rewrite. The server I'd just started was libSQL, the older SQLite fork. The command had worked exactly as intended.

I wanted to see what an application could read from a local file after another connection wrote to the server. The answer depends on which sync system you mean, and the name on the CLI tells you surprisingly little.

## Two engines and a hosted service

libSQL is the SQLite fork. Its server, `sqld`, accepts remote SQL connections and supports embedded replicas. The team maintains libSQL and builds new features in Turso Database, the SQLite-compatible rewrite in Rust that started as Limbo. As of November 2026, the latest published `sqld` release was `0.24.32` and the latest stable release of the Rust engine was `0.8.4`. [libSQL releases](https://github.com/tursodatabase/libsql/releases/tag/libsql-server-v0.24.32), [Turso Database releases](https://github.com/tursodatabase/turso/releases/tag/v0.8.4)

Turso Cloud is the hosted service. Its Go documentation lists drivers by engine and connection type. `go-libsql` gives an existing libSQL application embedded replicas. `tursogo` embeds the Rust engine and supports Turso Sync. If you inherit a service and want to know what it is using, check the imports and the server it talks to. [Turso Go driver reference](https://docs.turso.tech/sdk/go/reference)

## Start the local libSQL server

Install the Turso Cloud CLI, then open an empty working directory for the demo. I used the CLI version shown below. The second version is what I actually wanted to know.

{% highlight bash %}
{% raw %}
turso --version
# turso version v1.0.30
turso dev --version
# sqld sqld 0.24.32 (40c272de 2025-02-14)
turso dev --db-file local.db
{% endraw %}
{% endhighlight %}

The demo connects to the dev server at `127.0.0.1:8080`. Leave it running and open a second shell in the same directory.

My earlier example used Go. On this rerun, Go 1.27.4 on Apple Silicon rejected an LLVM bitcode section in the native archive that ships with `go-libsql` at revision `3051e37e6e04`. The build stopped before it made a connection. I switched to the JavaScript client to test the replica against the same libSQL server. [go-libsql's native library packaging](https://github.com/tursodatabase/go-libsql#notice)

## Read before and after sync

Install the exact client version used below. I ran it on Node.js 26.13.1.

{% highlight bash %}
{% raw %}
npm init -y
npm install --save-exact @libsql/client@0.17.2
{% endraw %}
{% endhighlight %}

Save the following as `replica.mjs`. The primary client sends SQL to the server. The replica reads from a local file and contacts the server when it syncs. The program seeds one row and syncs it to disk. Then the primary connection corrects the title.

{% highlight javascript %}
{% raw %}
import { createClient } from "@libsql/client";

const primaryUrl = "http://127.0.0.1:8080";
const primary = createClient({ url: primaryUrl });
const replica = createClient({ url: "file:replica.db", syncUrl: primaryUrl });

async function readTitle() {
  const result = await replica.execute("SELECT title FROM songs WHERE id = 1");
  return result.rows[0].title;
}

try {
  await primary.execute("CREATE TABLE songs (id INTEGER PRIMARY KEY, title TEXT NOT NULL)");
  await primary.execute("INSERT INTO songs VALUES (1, 'Gymnopedie No. 1')");
  await replica.sync();

  await primary.execute("UPDATE songs SET title = 'Gymnopédie No. 1' WHERE id = 1");
  console.log("Before sync:", await readTitle());
  await replica.sync();
  console.log("After sync: ", await readTitle());
} finally {
  replica.close();
  primary.close();
}
{% endraw %}
{% endhighlight %}

Run `node replica.mjs` once against the fresh dev server. The same query returns two different spellings.

{% highlight text %}
{% raw %}
Before sync: Gymnopedie No. 1
After sync:  Gymnopédie No. 1
{% endraw %}
{% endhighlight %}

The primary accepted the UPDATE before either SELECT ran. The first SELECT still returned the older title because it was reading the replica on disk. That's a useful case to test when a background job writes through one connection and a user expects a replica-backed page to show the change immediately. The two connections matter. A write through the replica connector itself can trigger the client's read-your-writes behavior.

## Check the vector index

The local server also lets you try libSQL's vector index. Paste the following into the SQL shell opened with `turso db shell http://127.0.0.1:8080`.

{% highlight sql %}
{% raw %}
CREATE TABLE docs (id INTEGER PRIMARY KEY, title TEXT, embedding F32_BLOB(4));
INSERT INTO docs VALUES (1, 'sqlite basics', vector('[0.9,0.1,0.0,0.0]'));
INSERT INTO docs VALUES (2, 'turso embedded replicas', vector('[0.85,0.15,0.05,0.0]'));
INSERT INTO docs VALUES (3, 'baking sourdough bread', vector('[0.0,0.0,0.1,0.95]'));
CREATE INDEX docs_embedding_idx ON docs (libsql_vector_idx(embedding));
SELECT id FROM vector_top_k('docs_embedding_idx', vector('[0.9,0.1,0.0,0.0]'), 2);
{% endraw %}
{% endhighlight %}

The index returned IDs `1` and `2`, the two database-related rows. Three hand-picked vectors tell me that the SQL path works locally. I'd need a real corpus to say anything about recall or speed.

## Summary

I would still use `turso dev` to reproduce an issue against a libSQL server. For an app that has to take writes while disconnected, I would test Turso Sync with its own local sync server. The Rust-based client writes to the local file first, then pushes and pulls explicitly. If two devices change the same row while offline, the order in which they push can determine which edit survives. That's a different test from the one I'd just run. [Turso Sync's push, pull and conflict model](https://turso.tech/blog/turso-sync-local-first-sqlite-with-push-and-pull)
